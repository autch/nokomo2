# kpisdk の補足（AI 向け）：全種類に共通

kpisdk_for_ai.md（入口）の続きです。先に入口の「読み方」と 0 節（設計の考え方）を読んでください。
節の番号は全ファイルを通した番号です（「6-1」はデコーダプラグインの 6 節の 1）。
ほかの節がどのファイルにあるかは、入口の「節の一覧」にあります。

## 1. IKpiFile

- 大きさ 0 の IKpiFile の GetBuffer は失敗（NULL・0）を返します。
- kpi_CreateMemoryFile は、大きさ 0 なら pBuffer が NULL でもかまいません（v3.17beta5 以降）。
- GetFileName は、ファイル名の部分だけを返します（フォルダの部分は付きません）。
  - プラグインが作って返す IKpiFile（アーカイブプラグインの展開結果、変換プラグインの変換結果など）の GetFileName も、
    ファイル名の部分だけを返してください（kpi_unarc.h にも「ディレクトリパスを除いたもの」とあります）。
  - 本体は、プラグインが返した IKpiFile の名前にフォルダの部分が含まれていれば取り除いてから、ほかのプラグインに渡します（v3.17beta5 以降）。
    受け取る側のプラグインも、念のため最後の \ か / より後ろだけを使うと安全です。
- kbrunkpi.exe 経由（プラグインを別のプロセスで動かす場合）では、GetBuffer で得たメモリはプロセスをまたぎません。
- 本体は IKpiFile::Abort を呼びません（呼ぶと落ちるプラグインが多かったため）。プラグインが作って返す IKpiFile は、Abort に対応しなくてかまいません（FALSE を返す。kpi.h）。

## 2. IKpiConfig（設定）

### 2-1. 値の取得・保存

- kpi_CreateConfig（kpi.cpp）は、ppConfig が NULL でも pdwPlatform を返します（それより前の本体では -1 のままです）。
- GetStr は、バッファが足りなければ空文字列を返します（途中で切った文字列は返しません）。
- 今の本体（v3.17beta5 以降）は、SetBin で保存できる大きさを 1MB まで、SetStr を 16KB までにしています（本体の都合の制限。0 を参照）。
  設定に大きなデータを持たせる必要があるなら、設定ではなくファイルにすることを考えてください。
- 設定の値にファイルのパスを持たせ、プラグインがそれを開く場合は、IKpiFolder::OpenFile で開くと、本体がファイルを開くときの扱いに従えます。
  自分で開く（CreateFile・ライブラリに渡すなど）場合は、プラグインで確かめてください。1 つの値に複数のパスを入れる形（| で区切るなど）は、
  本体からは 1 つの文字列にしか見えないので、パスごとの確認はプラグインがすることになります。

### 2-2. 呼んでよい時期

- 本体の中で動かす場合：モジュールが生きている間はいつでも使えます（モジュールの解放の処理の中も含みます）。
- kbrunkpi.exe 経由の場合：v3.17beta5 以降は、本体の中で動かす場合と同じです。
  - それより前の本体では、モジュールの解放の処理の中と、インスタンスをすべて解放してから次に本体から呼ばれるまでの間（プラグイン自身のスレッドから使う場合）は、
    Set の値は捨てられ、Get は既定値を返していました。
    古い本体でも動かす必要があるプラグインは、設定の保存を ApplyConfig の中か、インスタンスが生きている間に行うと安全です。

### 2-3. ApplyConfig の呼ばれ方

仕様の本文は kpi_decoder.h の IKpiDecoderModule::ApplyConfig にあります（ほかの種類のモジュールも同じです）。
「複数のキーの値がそろって初めて、どう保存すべきかが決まる設定」のための、少し癖のある仕組みです。

- 呼ばれ方：設定画面で「適用」すると、セクション単位で、そのセクションの中で値が変わったキーだけを、EnumConfig で列挙した順に 1 つずつ呼びます。
  最後に、同じセクションで cszKey に空文字列（L""）を渡して 1 回呼びます（このときの第 3 引数以降は無視してください）。
  - 値が変わったキーが 1 つもなければ、空文字列の呼び出しもありません。
  - 別のセクションは、そのときには呼ばれません。
- 呼ばれた時点では、IKpiConfig の値はまだ変わっていません。プラグインが SetXXX して初めて設定が変わります（SetXXX しなければ、何も変わりません）。
  - 値をモジュールの内部の変数に覚えるだけで SetXXX しないと、その値は保存されません。同じプロセスの今のインスタンスには効いているように見えても、
    後から作られるインスタンス（2 つめのインスタンス、kbrunkpi.exe で動く別のプロセスのインスタンス、プラグインの読み込み直しや本体の再起動の後）は
    IKpiConfig から設定を読むので、変更が反映されません。設定の値は必ず SetXXX で IKpiConfig に保存し、インスタンスはそこから読むようにしてください。
  - 渡される値は、EnumConfig で示した範囲に収まっていることを本体が保証します。そのままでよければ SetStr(cszSection, cszKey, cszValue) するだけで済みます
    （空文字列のキーで SetStr しても、本体が無視します）。
- 複数のキーの組み合わせで正しい値が決まる設定の扱い方：
  - 各キーの呼び出しでは、それぞれの値をとりあえず SetXXX しておきます。
  - 最後の空文字列の呼び出しで、セクション全体を読み直し、組み合わせとして正しい形に整えて SetXXX し直します。
  - ApplyConfig の中では、渡されたキー以外（EnumConfig で列挙していないキーや、ほかのセクションも含む）を GetXXX・SetXXX してかまいません。
  - 例 1：同じ種類の項目が多数並ぶ設定（検索するフォルダ 1〜64 など）。各キーはそのまま保存し、最後の呼び出しで全部を読み直して、
    重なりを除き、空きを前に詰めて保存し直す。
  - 例 2：ボタンのように使うキー（「すべて反転」「すべて解除」など）。呼ばれたら、同じセクションのほかのキーをまとめて書き換える。
  - 値の一貫性が問題になる場合は、EnumConfig で列挙しない別のキーに保存する方法もあります（画面上は 3 つの BOOL に見せ、保存は表示しない 1 つのキーにする、など。
    kpi_decoder.h に書かれています）。
- 戻り値：本体は、そのセクションの各キーと最後の空文字列の呼び出しの戻り値のうち、最も大きいものを使います
  （KPI_CFGRET_OK < NOTIFY < RELOAD_DATA < RELOAD_KPI < REBOOT_PLAYER < REBOOT_OS < UNKNOWN）。
  - 一度でも NOTIFY を返せば、最後の空文字列の呼び出しの後に、各インスタンスの UpdateConfig が呼ばれます。
  - 最後の呼び出しで OK を返しても、それより前のキーが返した値は取り消されません。キーごとに必要な値を返してください。
- kbrunkpi.exe 経由で別のプロセスで動いているインスタンスには、ApplyConfig は呼ばれず、UpdateConfig だけが届きます。設定はプロセスの間で共有されているので、
  インスタンスは設定を IKpiConfig から読み直してください。ApplyConfig の中でモジュールの内部の変数に設定を覚え、それをインスタンスが読む作りにすると、
  別のプロセスのインスタンスには反映されません（kpi_decoder.h にも書かれています）。

### 2-4. BIN の項目（設定画面を開くボタン）

KPI_CFG_TYPE_BIN の項目は、本体の設定画面ではボタンとして表示されます。プラグイン独自の設定画面を開くのに使えます
（kpi.h にも「ApplyConfig で設定画面を呼び出して設定を行う」とあります）。

- 本体の動き：その項目のボタンを押したときだけ、ApplyConfig(セクション, キー, 0, 0, L"") を呼びます。
  「適用」や「既定値に戻す」では、BIN の項目の ApplyConfig は呼びません。
- ApplyConfig の中で設定画面を開いて、閉じるまで戻らなくてかまいません。本体は戻るのを期限なしで待ちます
  （kbrunkpi.exe 経由のときも同じです）。開いている間、本体の設定画面は操作できません。
- 親にするウィンドウは渡されません。本体の中で動くときは、GetActiveWindow（本体の設定画面）を親にできます。
  kbrunkpi.exe 経由のときは GetActiveWindow が NULL になるので、親なしで開いてください（別のプロセスのウィンドウを親にしないこと）。
- 開いたウィンドウの破棄は、3-2 の決まりに従ってください（利用者が閉じたとき、またはモジュールの解放より前に、ApplyConfig を呼んだスレッドで破棄する）。
- STA が必要な画面（OleCreatePropertyFrame など）は、STA のスレッドを自分で作ってそこで開き、閉じるまで待ってください（3-3。
  kbrunkpi.exe 経由では、ApplyConfig を呼ぶスレッドは MTA です）。

## 3. スレッド・排他

### 3-1. 自分のロックを持ったまま本体の機能を呼ばない

- 決まり：kpi_CreateDecoder や IKpiConfig など、本体の機能を、プラグイン自身のロックを持ったまま呼ばないでください。
- 理由：kpi_CreateDecoder の先で別のプラグインが読み込まれ、kbrunkpi.exe 経由なら別のスレッドで設定の要求が動きます。
  その先から同じプラグインに別のスレッドで戻ってくると、固まります。

### 3-2. ApplyConfig で作ったウィンドウ

- 決まり：ApplyConfig の中で作ったウィンドウは、ApplyConfig を呼んだスレッドで、ユーザーが閉じたとき、またはモジュールの解放より前に破棄してください。
  閉じても隠すだけ、にはしないでください。
- kbrunkpi.exe の動き：ApplyConfig は専用のスレッドで呼び、モジュールの解放は別のスレッドで行います。モジュールを解放する前に、
  ApplyConfig 用のスレッドのウィンドウがすべてなくなるまで待ちます（残ったまま解放すると落ちるため）。
  ウィンドウが残っていると解放が進まず、本体に強制終了するかを尋ねるダイアログが出ます。
- 本体の中で動かす場合は、ApplyConfig もモジュールの解放もメインスレッドなので、モジュールの解放時に破棄しても動きます。
  kbrunkpi.exe 経由のときだけ違うので、上の決まりに従ってください。

### 3-3. COM

- 決まり：COM が必要なら、自分で作ったスレッドの中で、初期化と解放を対にして使ってください。
- 本体から呼ばれたスレッドの COM の状態は決めつけないでください。
  - 本体の中で動かす場合、メインスレッドは STA です。
  - kbrunkpi.exe のスレッドは MTA で初期化済みです。
- 呼ばれたスレッドで CoInitializeEx した場合は、成功したとき（S_OK・S_FALSE）だけ CoUninitialize してください。
  RPC_E_CHANGED_MODE のときは、今の種類のまま使い、CoUninitialize は呼ばないでください（呼ぶと本体の初期化を取り消してしまいます）。
- 呼ばれたスレッドで作った COM のオブジェクトを、別のメソッドで使わないでください（Open で作って Render で使う、など。メソッドごとにスレッドが違うことがあります。6-7）。
- STA が前提の処理（シェルのダイアログなど）は、STA のスレッドを自分で作って行ってください。

### 3-4. 同時に呼ばれるか

- KPI_MULTINST_INFINITE のとき、別々のインスタンスが別々のスレッドから同時に呼ばれることがあります（再生中に、Media エクスプローラのタイトル取得が動くなど）。
  ライブラリの大域変数（初期化済みの印、ログの設定など）が、同時に呼ばれても安全かを確かめてください。
  - kbrunkpi.exe 経由のときは、インスタンスごとに別の kbrunkpi.exe（別のプロセス）で動くので、このことは起きません。
    本体の中で動くこともあるので、安全にしておく必要はあります。
- 1 つのインスタンスのメソッドは、本体の中で動かす場合、別々のスレッドから呼ばれますが、同時には呼ばれません（6-7）。

## 5. kbrunkpi.exe 経由のときだけの違い

- kbrunkpi.exe 経由では、kpi_CreateDecoder（デコーダプラグインがほかのデコーダプラグインを使う）が失敗します（未実装）。
  本体の中で動いているときは使えます（6-14）。
- IKpiVideoWindow のウィンドウの指示（SetVisible など）は、本体の中では Seek・Render と同時に呼ばれることがありますが、
  kbrunkpi.exe 経由では Seek・Render の合間に呼ばれます（同時にはなりません。6-15）。
- 1・2-2・3-2・3-3・4 も参照してください。

## 8. 利用者へのお知らせ（メッセージログ。IKpiMessenger）

プラグインが利用者に知らせたいこと（ファイルを開けなかった理由・演奏を途中でやめた理由など）を、本体のウィンドウ
（「メッセージログ」）に出せます。どの種類のプラグインでも使えます。定義と細かい約束は kpi_message.h にあります（2026-11 追加）。
プラグインごとにウィンドウやメッセージボックスを作らずに済み、kbrunkpi.exe 経由のときも本体のウィンドウに出ます。

- 取得：kpi_CreateInstance の中で、第 3 引数を kpi_CreateMessenger（kpi_message.h で宣言。定義は kpi.cpp なので、kpi.cpp をプロジェクトに追加してください）に渡します。
  NULL が返ったら（対応していない本体・本体以外のアプリ）、何もしないか、自分で知らせてください。
- 呼び方：Notify(0, ファイル名, 本文)。どのスレッドから呼んでもよく、自分のロックを持ったままでもかまいません
  （本体は写して受け付けるだけで、すぐ戻ります）。DllMain の中からは呼ばないでください。
  - プラグイン名と日時は本体が付けます。本文に書かないでください。ファイル名は第 2 引数で渡します（IKpiFile::GetFileName のもの）。
  - 本文の長さと溜める件数には本体の上限があり、超えた分は切られます。同じお知らせが続くとまとめられます。
  - 本文に、ファイルのタグなど外から来た文字列を入れてもかまいません（制御文字は本体が置き換えます）。
- 決まり：利用者が読むものなので、同じことを何度も知らせないでください。
  - タグ取得のための Open（cpRequest == NULL）では知らせない。再生のための Open・再生中だけにします。
  - 「待ちますか」で利用者が待つのをやめたときは、「応答しなかった」こと自体は本人が分かっているので、何度も知らせない。
    止まった処理が残っていることと、本体を起動し直すとよいことを、1 回だけ知らせます（7-3）。
  - 1 つの出来事につき 1 回にする（演奏プラグインの GetStatus・デコーダの Render のように何度も呼ばれる所で知らせるなら、知らせたかを覚える）。
- 知らせるとよいこと（目安）：
  - ファイルを開けなかった理由：何に失敗したか（形式に対応していない・デコーダが見つからない・DRM など）と HRESULT。
    複数の方法（DS と MF など）を試すなら、それぞれの理由を 1 件にまとめます。
    本体は、デコーダプラグインで開けなかったときにほかのプラグインを試しません（.dsf と MIDI を除く）。開けなかったと知らせても、
    ほかのプラグインで開けていた、ということにはなりません。
  - 演奏を途中でやめた理由：
    - 演奏プラグインは、KPI_STATUS_ERROR を返すとき（Play の失敗を含む）に知らせます。
    - デコーダプラグインには「エラーで止まった」と本体に伝える手段がありません（Render が要求より少なく返すと、曲の終わりとして次へ進みます）。
      エラーのために少なく返すときに、理由を知らせてください。Seek の後でまたエラーになったら、また知らせてかまいません。
- HRESULT の説明文は FormatMessage で得られます。システムにないもの（DirectShow の VFW_E_XXX・Media Foundation の MF_E_XXX）は、
  システムのフォルダの quartz.dll・mferror.dll を LoadLibraryEx(フルパス, NULL, LOAD_LIBRARY_AS_DATAFILE) で読んで
  FORMAT_MESSAGE_FROM_HMODULE で得られます（名前だけで読まないこと。XP でも使えます）。
  DirectMusic のエラー（0x8878xxxx）には説明文がありません。
- 外部ツールの出力のような長いログを流す用途には使わないでください（1 件ずつの短いお知らせのためのものです）。

## 9. プラグイン用の作業フォルダ（IKpiWorkFolder）

プラグインが自分で作るファイル（変換した結果・外部のプログラムや DLL にファイル名で渡すためのコピーなど）の置き場所を、
本体から借りられます。どの種類のプラグインでも使えます。定義と細かい約束は kpi_workfolder.h にあります。
プラグインが自分で %TEMP% の下にフォルダを作り、ほかのプロセスと共有して使い終わったら消す、という管理をしなくて済みます。

- 使い分け：
  - 再生するファイルそのものを実ファイルとして使いたいだけなら、IKpiFile::GetRealFileW/A を使ってください（一時ファイルの作成と削除は本体が行います）。
  - アーカイブプラグインは、実ファイルとして展開する場合にこの口で作業フォルダを借ります（v3.17beta7 で IKpiUnArcModule::Open の
    cszOutputPath を廃止しました。KPI_UNARC_MODULE_VERSION は 3、IID も変わっています。kpi_unarc.h）。IKpiUnArc ごとに借りて、
    IKpiUnArc の解放まで持っておいてください（Extract で返した実ファイルは、IKpiUnArc の解放まで残っている必要があるためです）。
    借りられなかったときは、実ファイルが必要な展開だけを失敗させれば足ります（一覧の取得やメモリ上への展開は続けてかまいません）。
  - 変換プラグインも、実ファイルが必要な場合にこの口で作業フォルダを借ります（v3.17beta7 で IKpiConverterModule::Open の
    cszOutputPath を廃止しました。KPI_CONVERTER_MODULE_VERSION は 1、IID も変わっています。kpi_converter.h）。IKpiConverter ごとに借りて、
    IKpiConverter の解放まで持っておいてください（変換結果の実ファイルは、IKpiConverter の解放まで残っている必要があるためです。
    本体は変換結果の IKpiFile を解放してから IKpiConverter を解放します）。タグ取得だけのとき（Convert の ppDestFile が NULL）は借りずに済むよう、
    実際に変換するときに借りるのがおすすめです。借りられなかったときは、実ファイルが必要な変換だけを失敗させます。
  - 変換元のデータに書かれた名前（参照するファイル名など）で作業フォルダの中にファイルを作るときは、名前にパスの区切り（\ / :）や
    `..` が含まれていないことを確かめてください。確かめないと、作業フォルダの外に書き込めてしまいます。
  - それ以外で、プラグインが新しく作るファイルの置き場所が要るときに、この口を使います。
- 取得：kpi_CreateWorkFolder（kpi_workfolder.h で宣言。定義は kpi.cpp なので、kpi.cpp をプロジェクトに入れる）。引数は 2 通りです。
  - kpi_CreateInstance の第 3 引数（pUnknown）をそのまま渡す形。
  - IKpiUnkProvider を渡す形。Open の中など、後から作りたいときに使います。モジュールが kpi_CreateInstance の中で pUnknown から
    QueryInterface で IKpiUnkProvider を取り出して持っておき（AddRef されています。モジュールの解放時に Release）、必要になったときに渡します。
  - IKpiUnkProvider が得られないアプリから使われることもあるので、NULL のまま渡しても落ちないようにしてください（ヘルパー関数は NULL なら失敗を返します）。
- 本体の動き：
  - 呼ぶたびに、新しい空のフォルダを 1 つ作って返します。同時にいくつ作ってもかまいません。ほかのプラグイン・ほかのインスタンスとは共有されません。
  - GetPath は、末尾に \ の付いたフルパスを返します。最後の Release まで有効です。
  - 最後の Release で、本体がフォルダを中身ごと削除します。使用中で消せなかった分は、本体の終了時に削除されます。
  - kbrunkpi.exe 経由で動いているときも同じように使えます（フォルダを作る・消すのは本体です）。モジュールが生きている間は、いつ呼んでもかまいません。
    自分のロックを持ったまま呼んでも固まりません（本体はフォルダを作る・消すだけで、プラグインを呼び返しません）。
- 決まり：
  - Release の前に、中のファイルを閉じてください。子プロセスや外部の DLL に使わせている場合は、それを止めてから Release します。
    デコーダが子プロセスを持つなら、デコーダのデストラクタで「子プロセスを終わらせる → Release」の順にします。
  - 遅くとも、モジュールの解放時までに Release してください。モジュールが生きている間ずっと 1 つを持ち続ける使い方もできます。
  - 中にリンク（ジャンクション・シンボリックリンクなど）を作らないでください。
  - パスの長さは MAX_PATH 未満ですが、どれだけ短いかは決まっていません。中に作るファイルのフルパスが収まるかは、プラグインが確かめてください。
- KPI_WORKFOLDER_FLAG_ANSI：作業フォルダのパスが ANSI で表せることを求めます。ファイル名を ANSI でしか受け取れない部品に、中のファイルを渡すときに指定します。
  - 表せない場合（%TEMP% が ANSI で表せないユーザー名のフォルダにあるなど）は、失敗します。本体は、別の場所を探しません。
  - 中に作るファイルの名前を ANSI で表せるものにするのは、プラグインの役目です（port00.mid のような決まった名前にするなど）。
  - 未定義のフラグを指定すると失敗します。
- 失敗（*ppWorkFolder が NULL）：対応していない本体（v3.17beta6 以前）・本体以外のアプリ・作業フォルダを作れない・ANSI で表せない、の場合です。
  - 決まり：作業フォルダが必須なら、得られなかったときは Open を失敗させてください。代わりの場所を自分で作る必要はありません。
- どの単位で借りるかの目安：
  - 曲（デコーダ）ごとに一時ファイルを作るなら、デコーダごとに 1 つ借りて、デコーダの解放で返します。クロスフェードなどで 2 つのデコーダが同時に生きても、
    フォルダが別なのでファイル名が重なりません。
  - プロセスに 1 つの部品（複数のインスタンスを持てない DLL など）が使う共有のファイルを置くなら、モジュールの初期化で 1 つ借りて、モジュールの解放で返します。
